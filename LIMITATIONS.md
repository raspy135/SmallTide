# Limitations

Honest list of what SmallTide does and does not do today.

## Hardware & OS

- **Developed and tested on the AMD Radeon RX 9070 XT only.** The pre-built `smalltide-cli.exe` embeds two builds of its GPU kernels and loads the one for the card it finds; `smalltide.cmd probe` prints the choice and runs a test kernel.
  - `gfx1201`: RX 9070 XT, RX 9070, RX 9070 GRE, Radeon AI PRO R9700. Only the RX 9070 XT has been run. The others are the same architecture and load the same kernels.
  - `gfx1200`: RX 9060 XT, RX 9060. **Untested: no such card was available.** The kernels compile for it; whether they run correctly, and how fast, is not known. The 16 GB RX 9060 XT is the one that makes sense: the dense weights, KV cache and drafter take about 6 GB, which leaves an 8 GB card room for few experts.
  - The speeds, the resident-expert counts and the `.env.headless.example` / `.env.monitor.example` defaults in the README are for the RX 9070 XT (16 GB). If you run another card, please open an issue with the output of `smalltide.cmd probe`, whether it works or not.
  - If the driver names a card's architecture in a way the engine does not match, `SMALLTIDE_KERNEL_ARCH=gfx1201` (or `gfx1200`) in `.env` forces a kernel build.
  - RDNA 3 (`gfx1100`) and older are not supported: the kernels use RDNA 4 matrix (WMMA) instructions and do not compile for them.
- **Windows-first.** The direct NVMe expert store uses Win32 unbuffered I/O (`FILE_FLAG_NO_BUFFERING`), and resident VRAM budgeting queries Windows DXGI (`IDXGIAdapter3::QueryVideoMemoryInfo`). The Linux build ([README](README.md#linux)) reads experts with `O_DIRECT` and, having no DXGI, sizes the expert pools from the amdgpu driver's device-wide VRAM counters in sysfs. It has been run on one RX 9070 XT only, there is no pre-built Linux release, and the speeds and `.env` defaults in the README were measured on Windows.
- **AMD driver residency cap on 26.5.1–26.9.1.** Adrenalin drivers 26.5.1 through 26.9.1 had a KMD bug ([ROCm/TheRock#7221](https://github.com/ROCm/TheRock/issues/7221)) that capped per-process resident VRAM near half of the card (~8 GiB). **Adrenalin 26.10.44 or newer** is strongly recommended. If you must stay on an older affected driver, set `SMALLTIDE_RESIDENT_CAP=reservation` in `.env`.
- **Desktop VRAM contention (WDDM).** Because Windows shares your RX 9070 XT with the desktop compositor, browsers, and background apps (e.g. Creative Cloud, Discord, Electron apps), the resident expert budget depends on how much VRAM other apps hold at server startup, and it differs from one start to the next. SmallTide measures residency at startup (`fit_pools_to_resident`) and trims pools so weights never silently spill into ~10× slower PCIe system memory. On the development machine successive starts kept roughly 1,760 to 1,950 of the 3,072 experts resident, and decode speed moved by several tok/s with it. Freeing desktop VRAM before starting `serve` raises the count; it is fixed until the next restart.

## Model & Feature Scope

- **Inkling-2-Mini only.** SmallTide's dense loader, looped-transformer forward pass, `.stide` expert pack format, vision tower, and DSpark drafter are built specifically for [`thinkingmachines/Inkling-2-Mini`](https://huggingface.co/thinkingmachines/Inkling-2-Mini).
- **Image input: PNG and JPEG, sent as data.** Images go in as base64 (`image_url` with a `data:` URL, or an Anthropic-style base64 `source`). GIF and WebP are not decoded, `http(s)` image URLs are not fetched, and there is no video or audio input. Images are accepted by the HTTP server only (`smalltide-cli run` has no image option). An image costs one token per 40 × 40 pixel cell and is scaled down above `SMALLTIDE_VISION_MAX_TOKENS` (1,536). While an image is encoded (about 0.3–0.8 s) every other request on the server pauses.
- **No built-in API authentication.** The HTTP server binds to `0.0.0.0:8000` by default (configurable via `SMALLTIDE_HOST=127.0.0.1` in `.env`). Bind to `127.0.0.1` or place behind a reverse proxy if exposing beyond a trusted local network.
- **Threshold rescue is a speed/exactness trade-off.** Under the default `SMALLTIDE_RESCUE_MODE=threshold`, an expert that is not in VRAM is loaded inline when its share of the layer's routing weight is at least the zone's gate, up to per-step budgets of `33` / `30` / `35` (Prelude / Loop Core / Coda). The gates start at `0.07` and move while decoding so that each zone spends about 80% of its budget (`SMALLTIDE_RESCUE_AUTO_GATE=1`); misses below the gate, and those left once a zone's budget is spent, are skipped and the remaining routed experts renormalized. The figures that follow were measured with fixed gates of `0.08` / `0.09` and budgets of `18` / `35` / `20`, before the auto gate: 0.6-1.5% of routing weight on the prose, code and edit benchmarks, 4.5% on the random-token one, more on long agent sessions whose routing differs from the learned priors. The output is therefore not bit-identical to the full model's. The most likely next token is the full model's at about 96% of positions (`bench/agreement.py`: 12,086 positions over four workloads); no benchmark here measures answer quality beyond that. A rescue costs about 0.7 ms (most of it copying the expert from RAM to the card), so lower gates and higher budgets trade decode speed for fidelity: with no rescue at all the same run decodes about 1.5 times as fast.
- **`exact` is exact only without the drafter.** `SMALLTIDE_RESCUE_MODE=exact` copies in every missing expert on the single-token path and in prefill. The draft-verify passes of speculative decoding rescue only in `threshold` mode, so for exact expert execution set `SMALLTIDE_SPEC=0` as well.
- **Concurrent requests are slower.** When several requests decode at the same time they share batched rounds: each gets a fraction of the single-request speed and DSpark speculative decoding (`SMALLTIDE_SPEC=1`) is off for those rounds. Missing experts are rescued for the whole batch as in a draft-verify pass (`SMALLTIDE_BATCH_RESCUE=0` skips them instead, which is faster and was seen to end in repetition loops). A harness that sends side requests in parallel still gets better speed by sending them one at a time.
- **Page-locked memory is limited on this driver.** The GPU context is lost (`hipError_t=719`) somewhere above 6 GB of page-locked host memory in all. A RAM expert tier with 8 GB of it failed at startup; one with 5 GB failed in the server during a 26K-token prompt, where the prefix cache's snapshots (page-locked too, about 1 GB at the default `SMALLTIDE_PREFIX_TOKENS`) came on top. `SMALLTIDE_RAM_PINNED_GB` (off by default, capped at 3) puts that much of the RAM tier in page-locked memory, so those experts upload without the copy into the staging buffer: with 2 GB a 12K-token test decoded 3% faster and the server passed its validation requests. A larger `SMALLTIDE_PREFIX_TOKENS` draws on the same limited memory.
- **Answers are not reproducible run to run.** Which experts are resident changes with traffic, so the same prompt at `temperature=0` can produce different wording on different runs (in `threshold` mode).
- **Malformed tool calls are repaired only in known cases.** The server recovers tool-call JSON with bad escapes, unescaped inner quotes, trailing commas, or an escaped closing quote; other malformed calls from the model are returned as text.

## Disk

- **Disk footprint.** You need ~36 GB of free NVMe space during setup: ~21 GB for the Hugging Face checkpoint (`model-00001-of-00001.safetensors` + `mtp.safetensors`) plus ~14.7 GB for the 4 KB-aligned `experts.stide` pack. Both files are kept on disk (dense weights and the vision tower are read from the safetensors file; routed experts stream from `experts.stide`).
